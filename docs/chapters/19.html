    目安は約40分です。

    確認したバージョン

    2026-10-16 に、次を確認しました。

    • Configure Liveness, Readiness and Startup Probes
    • Resource Management for Pods and Containers
    • このクラスタの kubectl explain pod.spec.containers.livenessProbe
    • このクラスタの kubectl explain pod.spec.containers.readinessProbe
    • このクラスタの kubectl explain pod.spec.containers.resources.requests
    • このクラスタの kubectl explain pod.spec.containers.resources.limits

    クラスタは Kubernetes v1.37.0 です。クライアントは kubectl v1.37.1 です。

    ライブネスプローブは、explain では、コンテナが生きているかの定期検査です。失敗するとコンテナは再起動されます。レディネスプローブは、サービスとして受けられるかの定期検査です。失敗すると、Service の宛先から外れます。 failureThreshold は、成功したあとで失敗とみなすまでの連続失敗回数で、既定は 3 です。 periodSeconds は、検査の間隔の秒数で、既定は 10 秒です。

    requests は、explain では、必要な計算資源の最小量です。limits は、許される最大量です。requests は limits を超えられません。

    この章のゴール

    • ライブネスプローブ と レディネスプローブ を付けた Deployment を反映できる
    • リソース制限 の最小と最大を、マニフェストに書ける
    • 必ず失敗する検査で、コンテナが再起動されるのを確認できる

    前提

    第16章の Deployment、ConfigMap、Secret、Service を使います。アプリは、どのパスでも HTTP 200 と 設定から を返します。パスを /missing にしても、このアプリは失敗しません。失敗させたい検査は、終了コード 1 のコマンドにします。

    失敗しきい値 は、検査の失敗が続いたとみなすまでの回数です。この章では書いていないので、既定の 3 です。

    実行場所は、Ubuntu の端末です。Windows では、WSL2 の Ubuntu です。この章のコマンドは、どちらも同じです。

    確認テスト

    文章で答えてください。新しいコマンドを実行しなくても答えられます。

    問題1

    ライブネスプローブが失敗すると、Kubernetes は何をしますか。

    解答と解説

    そのコンテナを再起動します。

    explain では、ライブネスの検査が失敗するとコンテナは再起動されます。この章では、RESTARTS が 1 になった Pod を見ました。

    問題2

    レディネスプローブが失敗すると、Service はどうなりますか。

    解答と解説

    その Pod は、Service の宛先から外れます。

    explain では、レディネスの失敗で、コンテナは Service のエンドポイントから外されます。コンテナ自体の再起動は、ライブネスの役割です。

    問題3

    resources.requests は、limits より大きくできますか。

    解答と解説

    できません。requests は limits を超えられません。

    このクラスタの explain では、requests は最小量、limits は最大量で、requests は limits を超えられません。

    まとめ

    • ライブネスプローブ: コンテナが生きているかを定期的に調べ、失敗するとコンテナを再起動する検査です。
    • レディネスプローブ: サービスとして受けられるかを定期的に調べ、失敗すると Service の宛先から外す検査です。
    • リソース制限: コンテナが使う計算資源の最小量と最大量です。最小が requests、最大が limits です。
    • 失敗しきい値: 検査を失敗とみなすまでの連続失敗回数です。書いていないときの既定は 3 です。

    片付け

    失敗する検査は、壊す実験の手順3で、成功する定義へ戻してあります。Deployment、Service、ConfigMap、Secret は残します。第20章と第21章で、このクラスタを使います。
