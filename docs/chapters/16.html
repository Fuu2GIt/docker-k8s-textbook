    第16章 ConfigMapとSecret

    目安は約35分です。

    この章のゴール

    • ConfigMap に書いた文字を、アプリの応答にできる
    • Secret の値を、Pod の中の 環境変数 として読める
    • 文字列データ は書き込み用で、API から読み返す値ではないと説明できる

    前提

    第14章の Deployment と、第15章の Service を使います。イメージは memo:ch13 です。アプリは、環境変数 APP_MESSAGE があればその文字を返し、無ければ podから を返します。

    実行場所は、Ubuntu の端末です。Windows では、WSL2 の Ubuntu です。この章のコマンドは、どちらも同じです。

    1. Secret を作ります。
    cat > secret.yaml <<'EOF'
apiVersion: v1
kind: Secret
metadata:
  name: memo
  namespace: memo
type: Opaque
stringData:
  APP_TOKEN: local-only
EOF

    何をするコマンドか。 実行場所は、Ubuntu の端末です。同じファイルを samples/ch16/secret.yaml に置いてあります。 kind: Secret は、秘密の値の入れ物だと API に伝えます。 type: Opaque は、このファイルで指定した型です。 stringData は、このクラスタの explain では、バイナリではない秘密の値を文字列で渡す欄です。書き込み専用で、書いたキーと値は data へまとめて保存されます。API から読むとき、stringData は返ってきません。この値が文字列データです。 APP_TOKEN は local-only です。教科書の例なので、本番のパスワードは書かないでください。書いた値は、API では data に base64 で保存されます。base64 は、バイト列を決まった文字の並びへ移す方式です。暗号ではありません。公式の Secrets の良い実践 では、Secret の値は base64 の文字列になり、既定では暗号化されずに保存される、と書いてあります。同じページは、このファイルを共有したり、ソースの保管場所へ登録したりすると、読める人全員が秘密を見られる、とも書いています。Git は、ファイルの変更を履歴として残す仕組みです。この secret.yaml を Git へ上げないでください。上げた YAML は、履歴に残ります。

    kubectl apply -f "$HOME/docker-learn/ch16/configmap.yaml" --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 kubectl apply は、ファイルの定義をクラスタへ反映します。 -f は、ファイル名です。 --context kind-memo は、接続先です。この執筆環境では、同じ内容の samples/ch16/configmap.yaml を apply しました。

    1. Secret を反映します。
    kubectl apply -f "$HOME/docker-learn/ch16/secret.yaml" --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。手順5と同じ apply です。対象のファイルが Secret です。この執筆環境では、同じ内容の samples/ch16/secret.yaml を apply しました。

    終了ステータスは 0 でした。

    kubectl apply -f "$HOME/docker-learn/ch16/deployment.yaml" --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。既存の Deployment へ、環境変数を足した定義を反映します。この執筆環境では、同じ内容の samples/ch16/deployment.yaml を apply しました。

    期待する出力。

    終了ステータスは 0 でした。 configured は、新規作成ではなく更新です。

    出力が違うとき。 created と出たら、第14章の Deployment がありません。第14章から作り直してください。

    1. 更新が終わるまで待ちます。
    kubectl rollout status deployment/memo -n memo --timeout=90s --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。第14章と同じく、最新のロールアウトが終わるまで待ちます。 --timeout=90s は、90 秒の上限です。

    出力が違うとき。 timed out なら、kubectl get pods -n memo --context kind-memo で STATUS を見てください。

    curl -sS -D - http://127.0.0.1:30080/

    何をするコマンドか。 実行場所は、Ubuntu の端末です。Windows では、WSL2 の Ubuntu です。第15章と同じ curl です。 -s は進捗を出さず、-S はエラーを出し、-D - は受け取ったヘッダを画面へ出します。

    終了ステータスは 0 でした。ヘッダの改行に含まれていた CR は、表示では除いています。行の文字は同じです。Date は違ってよいです。 Content-Length: 12 と、本文の 設定から を確認してください。第15章の podから から変わっています。この curl は、第15章で書いた kube-proxy の切り替えのあとに実行しました。

    出力が違うとき。 本文が podから のままなら、新しい Pod がまだ入口に入っていません。手順8のあと、数秒待ってもう一度 curl してください。この執筆環境でも、切り替わった直後は前の文字が返ったことがありました。

    1. ConfigMap の値だけを見ます。
    kubectl get configmap memo -n memo --context kind-memo -o jsonpath='{.data.APP_MESSAGE}{"
"}'

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 kubectl get configmap は、ConfigMap を表示します。 -o jsonpath= は、kubectl get --help にある出力形式の1つで、指定した項目だけを出します。 {.data.APP_MESSAGE} は、data の APP_MESSAGE です。 {" "} は、最後に改行を出します。

    期待する出力。

    設定から

    終了ステータスは 0 でした。手順9の本文と、同じ文字です。

    出力が違うとき。 空なら、キーの名前が違います。configmap.yaml の APP_MESSAGE を確認してください。

    1. Secret の値が、Pod の環境変数にあるかを見ます。
    kubectl exec deployment/memo -n memo --context kind-memo -- printenv APP_TOKEN

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 kubectl exec は、コンテナの中でコマンドを実行します。 deployment/memo は、help の例にあるように、Deployment の最初の Pod を対象にします。 -n memo は、名前空間です。 --context kind-memo は、接続先です。 -- は、help では、その後ろをコンテナの中のコマンドとして分けます。 printenv APP_TOKEN は、環境変数 APP_TOKEN の値を出します。

    期待する出力。

    終了ステータスは 0 でした。Secret に書いた local-only が、Pod の環境変数に入っています。

    出力が違うとき。 command terminated with exit code 1 なら、その名前の環境変数がありません。手順7の apply が終わっているかを確認してください。

    1. Secret の一覧を見ます。
    kubectl get secret memo -n memo --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 kubectl get secret は、Secret の一覧です。値そのものは、この表示には出ません。

    期待する出力。

    NAME   TYPE     DATA   AGE
memo   Opaque   1      1s

    終了ステータスは 0 でした。AGE は違ってよいです。TYPE は Opaque で、DATA は 1 でした。キーが1つ、という意味の列です。 local-only という文字は、この一覧には出ていません。

    出力が違うとき。 NotFound なら、手順6が終わっていません。

    何が起きたか

    ConfigMap と Secret は、Pod の外に置いた値です。Deployment の env が、そのキーを環境変数へコピーします。アプリのコードは 設定から という文字を持っていません。環境変数が、初期値の podから を置き換えます。

    この執筆環境では、Secret の API の data.APP_TOKEN も読みました。中身は local-only でした。stringData は、読む側の結果には入っていませんでした。手順には、その読み出しコマンドは入れていません。手順11の printenv が、Pod から見た値です。

    data に入る値は base64 です。暗号ではありません。公式の Secrets では、Secret は既定では、API サーバの保存先 etcd に暗号化されずに置かれる、と書いてあります。etcd は、クラスタのデータを置く保存場所です。一覧に値が出なくても、API を読める人は値を取り出せます。手順3で書いたとおり、この secret.yaml は Git へ上げません。

    左の2つが、クラスタに保存した値です。右の Pod が、起動するときにそれを環境変数として受け取ります。

    壊してみる

    無い名前の環境変数を読みます。

    1. 存在しない名前を読みます。
    kubectl exec deployment/memo -n memo --context kind-memo -- printenv APP_MISSING

    何をするコマンドか。 実行場所は、Ubuntu の端末です。手順11と同じ exec です。名前だけ APP_MISSING にしています。ConfigMap にも Secret にも、このキーはありません。

    期待する出力。

    command terminated with exit code 1

    終了ステータスは 1 でした。 local-only のような値は出ていません。

    出力が違うとき。 何かの値が1行で出て、終了ステータスが 0 なら、その名前の環境変数が既にあります。名前を確認してください。

    command terminated with exit code 1 は、コンテナの中のコマンドが失敗した、と kubectl が返した文です。printenv は、指定した名前が無いと失敗します。

    確認テスト

    文章で答えてください。新しいコマンドを実行しなくても答えられます。

    問題1

    この章で応答が 設定から になったのは、アプリのどの仕組みですか。

    解答と解説

    環境変数 APP_MESSAGE があれば、その文字を返す仕組みです。

    アプリの初期値は podから です。ConfigMap の APP_MESSAGE が環境変数に入り、初期値を置き換えました。

    問題2

    stringData を kubectl get で読み返すと、どうなりますか。

    解答と解説

    stringData 自体は返ってきません。書いた値は data へ保存されます。

    このクラスタの explain では、stringData は書き込み専用で、API から読むときには出力されません。保存先の data は base64 で、既定では暗号化されません。YAML は Git へ上げません。

    問題3

    kubectl exec deployment/memo -- printenv APP_TOKEN の -- は、何のためですか。

    解答と解説

    その後ろを、コンテナの中で実行するコマンドとして分けるためです。

    kubectl exec --help では、コマンド側の引数と kubectl の引数を分けるときに、ダッシュ2つを使います。

    まとめ

    • ConfigMap: 設定の文字列を、Pod の外に置くリソースです。この章では APP_MESSAGE を入れました。
    • Secret: 秘密の値を、Pod の外に置くリソースです。保存は base64 だけで、既定では暗号化されません。一覧には値そのものは出ません。
    • 文字列データ: Secret に文字列を渡すための書き込み専用の欄です。API から読むときは返ってきません。

    片付け

    ConfigMap、Secret、Deployment、Service は消しません。第17章は、別の Pod でディスクを試します。アプリの Deployment はそのまま残します。
