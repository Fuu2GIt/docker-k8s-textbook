    第21章 学習の進め方と、総合演習

    目安は約70分です。

    この章のゴール

    • 文字を変えたアプリをイメージにして、kind のノードへ載せることができる
    • 初期値 より環境変数が優先されることを、応答の違いで確認できる
    • クラスタ削除 で、手元のクラスタを消すことができる

    前提

    第19章までの Deployment、ConfigMap、Secret、Service が、クラスタ memo で動いています。応答は 設定から です。アプリは、環境変数 APP_MESSAGE があればその文字を返し、無ければ初期値を返します。

    総合演習 は、アプリを自分で作り、イメージにして、Kubernetes で動かすまでの一連の練習です。この章では、初期値を 演習から に変えます。

    実行場所は、Ubuntu の端末です。Windows では、WSL2 の Ubuntu です。この章のコマンドは、どちらも同じです。

    何をするコマンドか。 実行場所は、Ubuntu の端末です。Windows では、WSL2 の Ubuntu です。 mkdir -p は、ディレクトリを作ります。 && は、左が成功したときだけ右を実行します。 cd は、カレントディレクトリを移します。

    期待する出力。

    何も表示されません。終了ステータスは 0 でした。

    出力が違うとき。 Permission denied なら、ホーム以外です。コマンドをコピーし直してください。

    1. 初期値を変えたアプリを作ります。
    cat > app.py <<'EOF'
import os
from http.server import BaseHTTPRequestHandler, HTTPServer


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        message = os.environ.get("APP_MESSAGE", "演習から")
        body = message.encode("utf-8")
        self.send_response(200)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


def main():
    port = int(os.environ.get("PORT", "8000"))
    server = HTTPServer(("0.0.0.0", port), Handler)
    print(f"listening on {port}", flush=True)
    server.serve_forever()


if __name__ == "__main__":
    main()
EOF

    何をするコマンドか。 実行場所は、Ubuntu の端末です。カレントディレクトリは $HOME/docker-learn/ch21 です。第13章と同じアプリで、初期値だけ 演習から です。APP_MESSAGE があれば、そちらを返します。同じファイルを samples/ch21/app.py に置いてあります。

    何も表示されません。終了ステータスは 0 でした。samples/ch21/app.py とバイト単位で一致しました。

    出力が違うとき。 Python のコードが画面に出たら、> が抜けています。cat から EOF までコピーし直してください。

演習から

    終了ステータスは 0 でした。ヘッダの改行に含まれていた CR は、表示では除いています。Date は違ってよいです。 Content-Length: 12 と、本文の 演習から を確認してください。このレスポンスの本文のあとには、追加の改行はありませんでした。環境変数が無くなったので、イメージの中の初期値が出ています。

    何が起きたか

    イメージを memo:ch21 に変えても、Pod は起動時に ConfigMap の APP_MESSAGE を受け取ります。アプリは環境変数を先に見るので、初期値の 演習から は出ません。環境変数の定義を外すと、初期値が出ます。コードを変えたことと、設定を変えたことは、別の操作です。

    左が、イメージを変えた直後です。右が、環境変数を外したあとです。どちらも同じイメージです。

    壊してみる

    存在しないコンテキストを指定します。

    1. 無いコンテキストで Pod を見ます。
    kubectl get pods -n memo --context kind-no-such

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 --context は、使う kubeconfig のコンテキストです。 kind-no-such は、作っていない名前です。クラスタが残っていても、この名前では接続しません。

    期待する出力。

    error: context "kind-no-such" does not exist

    終了ステータスは 1 でした。Pod の一覧は出ていません。

    出力が違うとき。 Pod の表が出たら、コンテキスト名が実在しています。kind-no-such をコピーし直してください。

    context was not found や does not exist は、kubeconfig にその接続先が無い、という意味です。クラスタの Pod が悪い、というエラーではありません。

    確認テスト

    文章で答えてください。新しいコマンドを実行しなくても答えられます。

    問題1

    イメージを memo:ch21 に変えた直後、応答が 設定から のままだったのは、なぜですか。

    解答と解説

    環境変数 APP_MESSAGE が残っていて、初期値より優先されたからです。

    アプリは APP_MESSAGE があればその文字を返します。初期値の 演習から は、環境変数が無いときだけ使います。

    問題2

    APP_MESSAGE- の末尾の - は、何をしますか。

    解答と解説

    その環境変数の定義を外します。

    kubectl set env --help の例では、ENV- が環境変数 ENV を外す書き方です。

    問題3

    kind delete cluster で --name を省略すると、どの名前を消しますか。

    解答と解説

    既定の kind です。この教科書のクラスタ名 memo は消えません。

    help では、--name の既定は kind です。この章では --name memo を付けます。

    まとめ

    • 総合演習: アプリを自分で作り、イメージにして、Kubernetes で動かすまでの一連の練習です。
    • 初期値: 環境変数が無いときに、アプリが使う文字です。環境変数があると、初期値は使われません。
    • クラスタ削除: kind のクラスタと、そのノードのコンテナを消す操作です。kind delete cluster --name memo がそれを行います。

    片付け

    クラスタを消します。イメージ memo:ch21 は、手元の Docker に残ります。次に同じ名前で作り直すときは、第12章からになります。

    1. クラスタを消します。
    kind delete cluster --name memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。Windows では、WSL2 の Ubuntu です。 kind delete cluster は、クラスタを消します。 --name memo は、消すクラスタの名前です。help では、すでに消してあっても成功で戻ります。

    期待する出力。

    Deleting cluster "memo" ...
Deleted nodes: ["memo-control-plane" "memo-worker"]

    終了ステータスは 0 でした。ノード memo-control-plane と memo-worker が消えています。

    出力が違うとき。 No kind clusters found と出るコマンドは、次の一覧です。delete が成功の行を出さなくても、終了ステータスが 0 なら、次で確認してください。

    1. クラスタの一覧を見ます。
    kind get clusters

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 kind get clusters は、残っている kind のクラスタ名を出します。

    期待する出力。

    No kind clusters found.

    終了ステータスは 0 でした。 memo は出ていません。

    出力が違うとき。 memo が残っているなら、手順1の --name memo が付いていません。もう一度、名前を付けて消してください。

    1. 消したあとのコンテキストを指定します。
    kubectl get nodes --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。クラスタを消したあと、以前のコンテキスト kind-memo でノードを見ます。kind は、削除のときにそのコンテキストも外します。

    期待する出力。

    Error in configuration: context was not found for specified context: kind-memo

    終了ステータスは 1 でした。ノードの表は出ていません。接続先の名前が、kubeconfig から無くなっています。

    出力が違うとき。 ノードの表が出たら、クラスタがまだ残っています。手順2で memo が無いかを確認してください。

    学習の進め方は、詰まった章の「壊してみる」と「出力が違うとき」に戻ることです。次に自分のアプリで通すときは、作業ディレクトリを $HOME/docker-learn の外に新しく作り、第6章、第9章、第12章からの順で、この章と同じ確認をします。
