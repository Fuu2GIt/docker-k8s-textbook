    第3部 Kubernetes

    第18章 障害を体験する

    目安は約45分です。

    この章のゴール

    • 動いている Pod を1つ消しても、Deployment が代わりを作ることを確認できる
    • ワーカーノードを止めると、STATUS が NotReady になると確認できる
    • 存在しないイメージを指定すると、イメージ取得失敗 の表示を読める

    前提

    第16章の Deployment memo が、名前空間 memo で2つ動いています。ラベル は app: memo です。Service は残しています。この章では、Deployment の定義ファイルは変えません。

    実行場所は、Ubuntu の端末です。Windows では、WSL2 の Ubuntu です。docker stop も、その Ubuntu で実行します。Windows の PowerShell から kind のコンテナを止める操作は、この執筆環境では実行していません。

    手を動かす

    1. 今の Pod を見ます。
    kubectl get pods -n memo -o wide --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。Windows では、WSL2 の Ubuntu です。 kubectl get pods は、Pod の一覧です。 -o wide は、ノード名などの列を足します。 -n memo は、名前空間です。 --context kind-memo は、接続先です。

    期待する出力。

    NAME                    READY   STATUS    RESTARTS   AGE   IP            NODE          NOMINATED NODE   READINESS GATES
memo-75d4d9868b-scxnq   1/1     Running   0          11m   10.244.1.12   memo-worker   <none>           <none>
memo-75d4d9868b-zb2cs   1/1     Running   0          11m   10.244.1.11   memo-worker   <none>           <none>

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。名前、IP、AGE は違ってよいです。この実行では、Running が2つで、どちらも NODE は memo-worker でした。次の手順で消すのは、1行目の memo-75d4d9868b-scxnq です。読者の画面では、Running の名前を1つ選んでください。

    出力が違うとき。 Running が2つでなければ、第16章のロールアウトが終わっていません。kubectl rollout status deployment/memo -n memo --timeout=90s --context kind-memo を実行してください。

    1. Running の Pod を1つ消します。
    kubectl delete pod memo-75d4d9868b-scxnq -n memo --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 kubectl delete pod は、指定した Pod を消します。名前は、手順1で選んだ Running の名前に置き換えてください。上の名前は、この執筆環境のものです。 -n memo は、名前空間です。 --wait の既定は true で、help では、リソースが無くなるまで待ってから戻ります。 --context kind-memo は、接続先です。

    期待する出力。

    pod "memo-75d4d9868b-scxnq" deleted from memo namespace

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。名前の部分は、消した Pod に置き換わります。

    出力が違うとき。 NotFound なら、その名前はもうありません。手順1の一覧から、Running の名前をコピーし直してください。

    1. 5秒待ちます。
    sleep 5

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 sleep は、GNU coreutils の help では、指定した秒数だけ止まります。 5 は 5 秒です。削除のコマンドは、Pod が無くなるまで待ってから戻ります。この 5 秒は、そのあとに足した待ち時間です。

    期待する出力。

    何も表示されません。2026-10-16 にこの執筆環境で実行し、そのあと次の一覧を取れました。終了ステータスは 0 です。

    出力が違うとき。 sleep が見つからない旨なら、Ubuntu の端末ではありません。

    1. 代わりの Pod を見ます。
    kubectl get pods -n memo --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。手順1と同じ種類の一覧です。 -o wide は付けていません。

    期待する出力。

    NAME                    READY   STATUS    RESTARTS   AGE
memo-75d4d9868b-pftqx   1/1     Running   0          36s
memo-75d4d9868b-zb2cs   1/1     Running   0          12m

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。名前と AGE は違ってよいです。消した memo-75d4d9868b-scxnq は、この一覧にありません。Running は2つのままです。新しい名前 memo-75d4d9868b-pftqx の AGE は 36s でした。削除が戻るまで待っているあいだに、代わりが作られていました。

    出力が違うとき。 消した名前がまだ Terminating なら、消える途中です。もう一度、この一覧を実行してください。 Running が1つなら、Deployment の replicas が 1 になっています。第16章のファイルは 2 です。

    1. コントロールプレーンのテイントを見ます。
    kubectl get node memo-control-plane --context kind-memo -o jsonpath='{range .spec.taints[*]}{.key}={.value}:{.effect}{"
"}{end}'

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 kubectl get node は、ノードを表示します。 -o jsonpath= は、指定した項目だけを出します。この式は、テイントの key、value、effect を1行にします。 memo-control-plane は、第12章のコントロールプレーンです。

    期待する出力。

    node-role.kubernetes.io/control-plane=:NoSchedule

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。 = の右が空なのは、value が空だったからです。effect は NoSchedule です。公式の Taints and Tolerations では、この印を許容しない新しい Pod を、そのノードへスケジュールしません。通常の Pod は、この印を許容していないので、コントロールプレーンへは新しく載りません。

    出力が違うとき。 空なら、そのノードにテイントがありません。kind のコントロールプレーンでは、この実行では付いていました。

    1. ワーカーノードのコンテナを止めます。
    docker stop memo-worker

    何をするコマンドか。 実行場所は、Ubuntu の端末です。Windows では、WSL2 の Ubuntu です。 docker stop は、help では、動いているコンテナを止めます。引数はコンテナ名です。kind のワーカーノードは、Docker コンテナ memo-worker です。 -t は、止める前に待つ秒数です。このコマンドでは付けていません。

    期待する出力。

    memo-worker

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。表示は、止めたコンテナの名前です。

    出力が違うとき。 No such container なら、クラスタ名が memo ではありません。docker ps -a で、kind のコンテナ名を見てください。

    1. 45秒待ちます。
    sleep 45

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 sleep 45 は、45秒止まります。止めた直後は、ノードの一覧がまだ Ready のことがあります。この執筆環境では、8秒後は Ready のままでした。45秒後の一覧を、次に載せます。

    期待する出力。

    何も表示されません。2026-10-16 にこの執筆環境で実行し、そのあとノードの一覧を取れました。終了ステータスは 0 です。

    出力が違うとき。 すぐに次のコマンドを打ってしまったら、Ready のままのことがあります。45秒待ってから、手順8を実行してください。

    1. ノードの状態を見ます。
    kubectl get nodes --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 kubectl get nodes は、ノードの一覧です。名前空間は付けません。ノードは、名前空間の外のリソースです。

    期待する出力。

    NAME                 STATUS     ROLES           AGE   VERSION
memo-control-plane   Ready      control-plane   32m   v1.37.0
memo-worker          NotReady   <none>          31m   v1.37.0

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。AGE は違ってよいです。 memo-control-plane は Ready のまま、memo-worker は NotReady でした。VERSION は、どちらも v1.37.0 でした。

    出力が違うとき。 両方 Ready なら、待ち時間が短いです。もう一度 sleep 45 を実行してから、この一覧を見てください。

    1. Pod がどこにいるかを見ます。
    kubectl get pods -n memo -o wide --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。ノードを止めたあとの Pod の場所を見ます。

    期待する出力。

    NAME                    READY   STATUS    RESTARTS   AGE   IP            NODE          NOMINATED NODE   READINESS GATES
memo-75d4d9868b-pftqx   1/1     Running   0          91s   10.244.1.13   memo-worker   <none>           <none>
memo-75d4d9868b-zb2cs   1/1     Running   0          13m   10.244.1.11   memo-worker   <none>           <none>

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。名前、IP、AGE は違ってよいです。この実行では、2つとも STATUS は Running のまま、NODE は memo-worker のままでした。コントロールプレーンへは移っていません。コントロールプレーンには NoSchedule があるため、通常の Pod はそこへ新しく載りません。

    出力が違うとき。 Pending が増えていても、ワーカーが NotReady なら、この章で見る状態です。次の手順でワーカーを戻します。

    1. ワーカーノードのコンテナを起動します。
    docker start memo-worker

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 docker start は、止まっているコンテナを起動します。引数は、手順6で止めた memo-worker です。

    期待する出力。

    memo-worker

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。表示は、起動したコンテナの名前です。

    出力が違うとき。 No such container なら、名前が違います。docker ps -a を見てください。

    1. ノードが Ready になるまで待ちます。
    kubectl wait --for=condition=Ready node/memo-worker --timeout=180s --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 kubectl wait は、条件を満たすまで待ちます。 --for=condition=Ready は、Ready になるまで待つ指定です。 node/memo-worker は、種類と名前です。 --timeout=180s は、180秒の上限です。

    期待する出力。

    node/memo-worker condition met

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。

    出力が違うとき。 timed out なら、docker ps で memo-worker が動いているかを見てください。止まっていれば、手順10をもう一度実行してください。

    1. ノードが戻ったかを見ます。
    kubectl get nodes --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。手順8と同じ一覧です。

    期待する出力。

    NAME                 STATUS   ROLES           AGE   VERSION
memo-control-plane   Ready    control-plane   32m   v1.37.0
memo-worker          Ready    <none>          31m   v1.37.0

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。AGE は違ってよいです。この実行では、両方の STATUS が Ready でした。

    出力が違うとき。 memo-worker が NotReady のままなら、手順11が終わる前です。待ちのコマンドを、もう一度実行してください。

    1. Pod を見ます。
    kubectl get pods -n memo -o wide --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。ノードが戻った直後の Pod です。

    期待する出力。

    NAME                    READY   STATUS    RESTARTS   AGE   IP            NODE          NOMINATED NODE   READINESS GATES
memo-75d4d9868b-pftqx   1/1     Running   0          93s   10.244.1.13   memo-worker   <none>           <none>
memo-75d4d9868b-zb2cs   1/1     Running   0          13m   10.244.1.11   memo-worker   <none>           <none>

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。名前、IP、AGE は違ってよいです。この実行では、2つとも Running で、NODE は memo-worker、RESTARTS は 0 でした。IP は、止める前の一覧と同じ 10.244.1.13 と 10.244.1.11 でした。

    出力が違うとき。 RESTARTS が 1 でも、Running なら次へ進んでください。この章のあとの一覧では、古い Pod の RESTARTS が 1 になっていました。

    何が起きたか

    Deployment は、Pod が1つ消えると、レプリカの数を戻すために新しい Pod を作ります。ワーカーを止めると、そのノードは NotReady になります。この実行では、Pod は NotReady のワーカーに残ったまま、Running と表示されていました。コントロールプレーンは Ready のままで、通常の Pod を新しく載せる印にはなっていません。

    左が止めたワーカーです。Pod の表示は Running のままでした。右のコントロールプレーンは Ready で、NoSchedule が付いています。

    壊してみる

    存在しないイメージ名へ更新します。

    1. イメージ名を、無いタグに変えます。
    kubectl set image deployment/memo web=memo:missing-tag -n memo --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。 kubectl set image は、コンテナのイメージを更新します。 web=memo:missing-tag は、コンテナ web のイメージを memo:missing-tag にする指定です。この名前のイメージは、ノードにも、外のレジストリにも用意していません。

    期待する出力。

    deployment.apps/memo image updated

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。コマンド自体は受け付けられます。失敗は、次の Pod の STATUS に出ます。

    出力が違うとき。 not found なら、Deployment の名前か名前空間が違います。

    1. 12秒待ちます。
    sleep 12

    何をするコマンドか。 実行場所は、Ubuntu の端末です。新しい Pod がイメージを取りにいく時間です。 12 は 12 秒です。

    期待する出力。

    何も表示されません。2026-10-16 にこの執筆環境で実行し、そのあと一覧を取れました。終了ステータスは 0 です。

    出力が違うとき。 すぐに一覧を見ると、STATUS が ContainerCreating のことがあります。12秒待ってから、次を実行してください。

    1. Pod の状態を見ます。
    kubectl get pods -n memo --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。新しい Pod が、イメージを取れたかを見ます。

    期待する出力。

    NAME                    READY   STATUS         RESTARTS      AGE
memo-59d7f84d5b-l4h56   0/1     ErrImagePull   0             12s
memo-75d4d9868b-pftqx   1/1     Running        1 (13s ago)   105s
memo-75d4d9868b-zb2cs   1/1     Running        1 (13s ago)   13m

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。名前と AGE は違ってよいです。新しい Pod memo-59d7f84d5b-l4h56 は、READY が 0/1、STATUS が ErrImagePull でした。これがイメージ取得失敗の表示です。古い2つの Pod は Running のままで、RESTARTS は 1 になっていました。この一覧だけでは、その1回の理由は切り分けていません。見てほしいのは、ErrImagePull の行です。

    出力が違うとき。 ImagePullBackOff と出ることもあります。イメージを取れず、次の取得まで待っている状態です。タグ名が memo:missing-tag なら、この章で見る失敗です。

    1. 直前の定義へ戻します。
    kubectl rollout undo deployment/memo -n memo --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。第14章と同じく、直前のリビジョンへ戻します。 --to-revision は付けていません。既定は、最後のリビジョンです。

    期待する出力。

    Warning: resource deployments/memo was previously managed with 'kubectl apply'. Rolling back will not update the kubectl.kubernetes.io/last-applied-configuration annotation, which may cause unexpected behavior on future 'kubectl apply' operations. Consider using 'kubectl apply' with your previous configuration file instead.
deployment.apps/memo rolled back

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。1行目は、apply で管理していた Deployment を undo すると、最後に apply した内容の記録は戻らない、という警告です。2行目の rolled back が出ていれば、戻る操作は受け付けられています。

    出力が違うとき。 error: で終わるなら、戻る先がありません。手順1の set image のあとであるかを確認してください。

    1. 戻り終わるまで待ちます。
    kubectl rollout status deployment/memo -n memo --timeout=180s --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。戻した定義の Pod が揃うまで待ちます。 --timeout=180s は、180秒の上限です。

    期待する出力。

    deployment "memo" successfully rolled out

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。この実行では、途中の Waiting の行は出ず、すぐに成功の行が出ました。古い Pod が Running のままだったためです。

    出力が違うとき。 timed out なら、kubectl get pods -n memo --context kind-memo で STATUS を見てください。

    1. 戻ったあとの Pod を見ます。
    kubectl get pods -n memo --context kind-memo

    何をするコマンドか。 実行場所は、Ubuntu の端末です。失敗した Pod が消える途中かを見ます。

    期待する出力。

    NAME                    READY   STATUS        RESTARTS      AGE
memo-59d7f84d5b-l4h56   0/1     Terminating   0             13s
memo-75d4d9868b-pftqx   1/1     Running       1 (14s ago)   106s
memo-75d4d9868b-zb2cs   1/1     Running       1 (14s ago)   13m

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。名前と AGE は違ってよいです。 ErrImagePull だった Pod は Terminating で、古い2つは Running でした。

    出力が違うとき。 ErrImagePull の Pod がまだ Running 扱いで残っていても、手順5が成功していれば、しばらくすると消えます。もう一度、この一覧を実行してください。

    1. 3秒待ってから、応答を見ます。
    sleep 3

    何をするコマンドか。 実行場所は、Ubuntu の端末です。入口が安定するまでの短い待ちです。 3 は 3 秒です。

    期待する出力。

    何も表示されません。2026-10-16 にこの執筆環境で実行し、終了ステータスは 0 でした。

    出力が違うとき。 待たずに次を実行しても、設定から が返るなら成功です。

    1. アプリが応答するかを見ます。
    curl -sS -D - http://127.0.0.1:30080/

    何をするコマンドか。 実行場所は、Ubuntu の端末です。Windows では、WSL2 の Ubuntu です。第15章と同じ curl です。失敗した更新のあと、入口がまだアプリを返すかを見ます。

    期待する出力。

    HTTP/1.0 200 OK
Server: BaseHTTP/0.6 Python/3.12.15
Date: Fri, 16 Oct 2026 18:43:33 GMT
Content-Type: text/plain; charset=utf-8
Content-Length: 12

設定から

    この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。Date は違ってよいです。 HTTP/1.0 200 OK と、本文の 設定から を確認してください。存在しないイメージの Pod は入口に入っておらず、前の Pod が応答しています。

    出力が違うとき。 Couldn't connect to server なら、ワーカーがまだ止まっています。手順10から戻してください。

    ErrImagePull は、指定したイメージを取れなかった、という意味です。コマンドが image updated と成功しても、Pod は動きません。rollout undo で、直前の動く定義へ戻せます。

    文章で答えてください。新しいコマンドを実行しなくても答えられます。

    問題1

    Pod を1つ消したあとに、Running が2つのままなのは、なぜですか。

    解答と解説

    Deployment のレプリカが 2 で、足りない分の Pod を ReplicaSet が作るからです。

    この実行では、消した名前は一覧から無くなり、別の名前の Pod が Running になっていました。

    問題2

    ワーカーが NotReady のとき、Pod はコントロールプレーンへ移りましたか。

    解答と解説

    この実行では移りませんでした。NODE は memo-worker のままでした。

    コントロールプレーンのテイント effect は NoSchedule です。通常の Pod は、そこへ新しく載りません。

    問題3

    memo:missing-tag を指定したとき、kubectl set image 自体は失敗しましたか。

    解答と解説

    失敗していません。終了ステータスは 0 で、image updated と出ました。

    失敗は Pod の STATUS に ErrImagePull として出ます。コマンドの成功と、Pod の起動は別です。

    まとめ

    • NotReady: ノードの STATUS が、準備できていないことを示す値です。この章では、コンテナを止めたワーカーがこうなりました。
    • テイント: ノードに付けた印です。NoSchedule は、その印を許容しない新しい Pod を、そのノードへ載せません。
    • イメージ取得失敗: 指定したイメージをノードが取れない状態です。一覧の STATUS は ErrImagePull になります。

    片付け

    この章で止めたワーカーは、手順10で起動し、手順12で Ready に戻しています。失敗したイメージの更新は、rollout undo で戻しています。Deployment、Service、ConfigMap、Secret は消しません。クラスタも消しません。
