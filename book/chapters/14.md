## この章のゴール

- [[Deployment]] で、同じ定義の [[Pod]] を複数同時に動かすことができる
- イメージを差し替え、台数が揃うまで待つことができる
- [[ロールバック]] で、直前の定義へ戻すことができる

## 前提

第13章の名前空間 `memo` と、イメージ `memo:ch13` を使います。Pod 名 `memo` は、第13章の片付けで消してあります。同じ名前の Deployment を作っても、種類が違うので衝突しません。

[[レプリカ]] は、同じ Pod の定義を同時に動かす数です。この章では、最初 2 です。

[[ReplicaSet]] は、その数の Pod を保つリソースです。公式の [Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) では、Deployment が ReplicaSet を作り、ReplicaSet が Pod を作ります。Pod を1つずつ自分で作り直す必要はありません。

実行場所は、Ubuntu の端末です。Windows では、[[WSL2]] の Ubuntu です。この章のコマンドは、どちらも同じです。

6. Deployment のマニフェストを作ります。

```bash
cat > deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: memo
  namespace: memo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: memo
  template:
    metadata:
      labels:
        app: memo
    spec:
      containers:
      - name: web
        image: memo:ch13
        imagePullPolicy: IfNotPresent
        ports:
        - containerPort: 8000
EOF
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。カレントディレクトリは `$HOME/docker-learn/ch14` です。同じファイルを `samples/ch14/deployment.yaml` に置いてあります。

`apiVersion: apps/v1` と `kind: Deployment` は、これが Deployment だと API に伝えます。 `metadata.name` は `memo` です。 `metadata.namespace` は `memo` です。 `spec.replicas` は、このクラスタの explain では、望ましい Pod の数です。指定が無いときの既定は 1 です。ここでは 2 です。 `selector.matchLabels` は、explain では、どの Pod をこの Deployment の対象にするかのラベルです。Pod テンプレートのラベルと一致している必要があります。ここでは `app: memo` です。 `template` は、作る Pod の型です。 `image: memo:ch13` は、第13章のイメージです。更新は、あとから `memo:ch14` へ差し替えます。 `imagePullPolicy: IfNotPresent` は、第13章と同じく、ノードにイメージが無いときだけ取得します。

`spec.strategy.type` は、このクラスタの explain では、既定が `RollingUpdate` です。古い ReplicaSet を少しずつ減らし、新しい ReplicaSet を少しずつ増やします。このファイルでは strategy を書いていないので、その既定です。

期待する出力。

## 壊してみる

レプリカに、0 より小さい数を渡します。

1. 不正な数で scale します。

```bash
kubectl scale deployment/memo --replicas=-1 -n memo --context kind-memo
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。 `--replicas` は、help では新しい望ましい数です。 `-1` は、0 より小さいので受け付けません。このコマンドは、2026-10-16 に、すでに Deployment がある状態で実行しました。

期待する出力。

```text
error: The --replicas=COUNT flag is required, and COUNT must be greater than or equal to 0
```

この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 1 でした。 `scaled` とは出ていません。サーバが台数を変えた、という表示はありません。

出力が違うとき。 `deployment.apps/memo scaled` と出たら、`-1` が別の数になっています。コマンドをコピーし直してください。

`error:` で始まる行は、クライアントが拒否した、という意味です。0 以上の整数だけが、レプリカの数になります。

## 確認テスト

文章で答えてください。新しいコマンドを実行しなくても答えられます。

:::quiz
`spec.replicas` が 2 の Deployment は、何を望ましい状態として持ちますか。
:::answer
同じ Pod の定義が、2つ同時に動いている状態です。
:::explain
このクラスタの explain では、replicas は望ましい Pod の数です。指定が無いときの既定は 1 です。
:::

:::quiz
`kubectl set image` でイメージを変えたとき、古い Pod はどうなりますか。
:::answer
新しい ReplicaSet の Pod が増え、古い Pod は Terminating になって消えます。
:::explain
strategy の既定は RollingUpdate です。この章の実行では、新しい名前の Pod が Running になり、古い名前は Terminating でした。
:::

:::quiz
`kubectl rollout undo` で `--to-revision` を省略すると、どこへ戻りますか。
:::answer
最後のリビジョンです。help の既定は 0 で、それが最後のリビジョンを指します。
:::explain
この章では、`memo:ch14` へ差し替えた直後に undo したので、差し替える前の `memo:ch13` の ReplicaSet に戻りました。
:::

## まとめ

- **Deployment**: Pod と ReplicaSet の望ましい状態を宣言し、制御された速さでそこへ寄せるリソースです。
- **レプリカ**: 同じ Pod の定義を、同時に動かしたい数です。`spec.replicas` に書きます。
- **ロールバック**: Deployment を、前のリビジョンの定義へ戻す操作です。`kubectl rollout undo` がそれを行います。
- **ReplicaSet**: 指定した数の Pod を保つリソースです。Deployment がこれを作り、直接は管理しません。

## 片付け

この章の Deployment は消しません。第15章で、この Pod へ届く入口を作ります。レプリカは 3 のままです。第16章のマニフェストを apply すると、2 に戻ります。イメージ `memo:ch13` と `memo:ch14` も残します。
