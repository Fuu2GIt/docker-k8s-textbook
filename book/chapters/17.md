## この章のゴール

- [[永続ボリューム要求]] を作り、Pod が使うまで Pending だと確認できる
- 書き込んだ文字を、その Pod を消したあとに別の Pod から読める
- [[アクセスモード]] の値が不正だと、作成が拒否されると確認できる

## 前提

第13章のイメージ `memo:ch13` が、kind のノードに載っています。名前空間 `memo` と、第16章の Deployment は残します。この章で作るのは、書き込み用と読み取り用の Pod と、ディスクの要求だけです。

第8章の [[ボリューム]] は、Docker がコンテナのために持つ保存場所です。この章の永続ボリューム要求は、Kubernetes の Pod がディスクを求める宣言です。同じ言葉でも、指すものは違います。

[[ストレージクラス]] は、ディスクの用意の仕方に付けた名前です。[[再起動ポリシー]] は、Pod の中のコンテナが終わったあと、もう一度起動するかの指定です。このクラスタの explain では、Always、OnFailure、Never のいずれかで、既定は Always です。

実行場所は、Ubuntu の端末です。Windows では、[[WSL2]] の Ubuntu です。この章のコマンドは、どちらも同じです。

2. ストレージクラスを見ます。

```bash
kubectl get storageclass standard --context kind-memo
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。 `kubectl get storageclass` は、ストレージクラスの一覧です。 `standard` は、その名前です。 `--context kind-memo` は、接続先です。

```text

standard   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  35m
```

終了ステータスは 0 でした。AGE は違ってよいです。PROVISIONER は `rancher.io/local-path`、RECLAIMPOLICY は `Delete`、VOLUMEBINDINGMODE は `WaitForFirstConsumer` でした。公式の [Storage Classes](https://kubernetes.io/docs/concepts/storage/storage-classes/#volume-binding-mode) では、WaitForFirstConsumer は、その要求を使う Pod ができるまで、ボリュームの結合と用意を遅らせます。

出力が違うとき。 `NotFound` なら、クラスタが第12章の kind ではありません。`kubectl get storageclass --context kind-memo` で名前を見てください。

3. 永続ボリューム要求を作ります。

```bash
cat > pvc.yaml <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: memo-data
  namespace: memo
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: standard
  resources:
    requests:
      storage: 10Mi
EOF
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。同じファイルを `samples/ch17/pvc.yaml` に置いてあります。 `kind: PersistentVolumeClaim` は、永続ボリューム要求だと API に伝えます。名前は `memo-data` です。名前空間は `memo` です。 `accessModes` は、explain では、ボリュームに持たせたいアクセスの仕方です。 `ReadWriteOnce` は、[Persistent Volumes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/) の説明では、1つのノードから読み書きでマウントできるモードです。 `storageClassName: standard` は、explain では、要求するストレージクラスの名前です。 `storage: 10Mi` は、要求する容量です。

期待する出力。

何も表示されません。終了ステータスは 0 でした。`samples/ch17/pvc.yaml` とバイト単位で一致しました。

出力が違うとき。 YAML が画面に出たら、`>` が抜けています。コマンドをコピーし直してください。

```yaml file=samples/ch17/pvc.yaml

  namespace: memo

  - ReadWriteOnce

```

## 壊してみる

アクセスモードに、一覧に無い値を書きます。

1. 不正な値で要求を作ります。

```bash
kubectl apply -f - --context kind-memo <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: memo-bad
  namespace: memo
spec:
  accessModes:
  - NotAMode
  resources:
    requests:
      storage: 10Mi
EOF
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。 `kubectl apply -f -` は、ファイル名の代わりに、標準入力の YAML を読みます。 `NotAMode` は、アクセスモードとして定義されていない値です。名前は `memo-bad` です。

期待する出力。

```text
The PersistentVolumeClaim "memo-bad" is invalid: spec.accessModes: Unsupported value: "NotAMode": supported values: "ReadOnlyMany", "ReadWriteMany", "ReadWriteOnce", "ReadWriteOncePod"
```

終了ステータスは 1 でした。 `memo-bad` は作られていません。この確認のとき、名前空間 `memo` には他の要求も残っていなかったので、`kubectl get pvc -n memo` は `No resources found in memo namespace.` でした。読者がこの章の順番で実行するときは、`memo-data` が表示されていてよいです。一覧に `memo-bad` が無いことを確認してください。

出力が違うとき。 `persistentvolumeclaim/memo-bad created` と出たら、値が受け付けられています。`kubectl delete pvc memo-bad -n memo --context kind-memo` で消してください。

`Unsupported value` は、その欄が受け付ける値の一覧に入っていない、という意味です。このクラスタが示す値は、ReadOnlyMany、ReadWriteMany、ReadWriteOnce、ReadWriteOncePod です。

## 確認テスト

文章で答えてください。新しいコマンドを実行しなくても答えられます。

:::quiz
要求を作った直後の STATUS が Pending だったのは、なぜですか。
:::answer
ストレージクラスの結合モードが WaitForFirstConsumer で、使う Pod がまだ無かったからです。
:::explain
公式の説明では、このモードは、要求を使う Pod ができるまで、ボリュームの結合と用意を遅らせます。Pod のあと、STATUS は Bound になりました。
:::

:::quiz
書き込み用の Pod を消したあとに、文字が残っていたことを、どの出力で確認しましたか。
:::answer
読み取り用の Pod のログが `残るメモ` だったことです。
:::explain
2つの Pod は別の名前です。同じ要求 `memo-data` を、`/data` に見せました。
:::

:::quiz
`restartPolicy: Never` を書いたのは、なぜですか。
:::answer
終わったコマンドを、既定の Always で繰り返さないためです。
:::explain
explain では、再起動ポリシーの既定は Always です。Never にすると、正常に終わった Pod の phase は Succeeded で止まれます。
:::

## まとめ

- **永続ボリューム要求**: Pod が欲しい容量とアクセスの仕方を書いたリソースです。Pod を消しても、要求は残ります。
- **ストレージクラス**: ディスクの用意の仕方に付けた名前です。このクラスタの `standard` は、最初の Pod まで結合を待ちます。
- **アクセスモード**: ボリュームをどうマウントするかの指定です。ReadWriteOnce は、1つのノードから読み書きできるモードです。
- **再起動ポリシー**: コンテナが終わったあと、もう一度起動するかの指定です。既定は Always で、この章の2つの Pod は Never です。
