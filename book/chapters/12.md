## この章のゴール

- [[kind]] で、手元の Docker の上に [[クラスタ]] を作ることができる
- `kubectl` で、[[ノード]] の一覧を見ることができる
- 作ったクラスタを、次の章まで残すことができる

## 前提

第2章の Docker と、第11章の [[Kubernetes]] を使います。Docker が動いていることを、`docker ps` で確認してから始めてください。

[[ノード]] は、Pod を動かす場所です。kind では、その場所が Docker コンテナになります。Pod は、第13章で作ります。

この章は、クラスタを2台のノードで作ります。1台はコントロールプレーン、もう1台はワーカーです。第18章で、ワーカーだけを止めます。コントロールプレーンの 30080 番は、ホストの 127.0.0.1 の 30080 番へつないでおきます。第15章で、自分のパソコンから開くためです。kind の説明では、`listenAddress` を `127.0.0.1` にすると届き方に影響することがある、と書いてあります。この環境では、コントロールプレーンのコンテナに `127.0.0.1:30080->30080/tcp` が付いていることを、`docker ps` で見ました。

実行場所は、原則として Ubuntu の端末です。Windows では、[[WSL2]] の Ubuntu です。kind と kubectl の取得だけは、Windows の PowerShell の手順が違います。

```text
Set kubectl context to "kind-memo"
You can now use your cluster with:

kubectl cluster-info --context kind-memo

Have a nice day! 👋
```

この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。絵文字と、`Ready after` の秒数は違ってよいです。 `Creating cluster "memo"` と、`Set kubectl context to "kind-memo"` が出てください。

`kind-memo` は、[[kubeconfig]] の中の接続先の名前です。kubeconfig は、kubectl がクラスタへ接続するための設定ファイルです。既定の場所は `$HOME/.kube/config` です。kind が、このファイルへ `kind-memo` を書きました。

出力が違うとき。 `node(s) already exist` なら、同じ名前のクラスタが残っています。この章の壊す実験を、先に実行していなければ、第21章までそのクラスタを使ってください。作り直す必要はありません。 `timed out` なら、5 分で Ready になりませんでした。`kubectl get nodes --context kind-memo` を実行し、STATUS を見てください。

9. コントロールプレーンのアドレスを見ます。

```bash
kubectl cluster-info --context kind-memo
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。 `kubectl cluster-info` は、コントロールプレーンと、クラスタのサービスのアドレスを出します。 `--context` は、`kubectl options` では、使う kubeconfig のコンテキストの名前です。コンテキストは、接続先を選ぶ名前です。ここでは `kind-memo` です。

期待する出力。

```text
Kubernetes control plane is running at https://127.0.0.1:39865
```

この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。ポート番号は違ってよいです。 `Kubernetes control plane is running` と `CoreDNS is running` が出てください。

出力が違うとき。 `connection refused` なら、クラスタがまだ Ready ではありません。手順8のログの最後を見てください。 `context was not found` なら、名前が `kind-memo` ではありません。手順8の `Set kubectl context` の行を見てください。

10. ノードの一覧を見ます。

```bash
kubectl get nodes --context kind-memo
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。 `kubectl get` は、リソースの一覧を出します。 `nodes` は、ノードです。 `--context kind-memo` は、手順9と同じ接続先です。


この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。AGE の時間は違ってよいです。名前 `memo-control-plane` と `memo-worker`、STATUS が両方 `Ready`、VERSION が `v1.37.0` であることは一致させてください。ワーカーの ROLES は `<none>` でした。

## 壊してみる

同じ名前でもう一度作り、エラーを読みます。

1. 同じ名前でクラスタを作ります。

```bash
kind create cluster --name memo
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。 `--name memo` は、すでに作ったクラスタの名前です。設定ファイルは渡しません。kind は、同じ名前のノードが残っていると作成を始めません。

期待する出力。

```text
ERROR: failed to create cluster: node(s) already exist for a cluster with the name "memo"
```

この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 1 でした。

出力が違うとき。 `Creating cluster "memo"` から先へ進んだら、先にクラスタが消えています。第21章の削除を、まだ実行しないでください。手順8から作り直してください。

`already exist` は、その名前のノードが既にある、という意味です。失敗なので、今のクラスタはそのまま残ります。

## まとめ

- **kind**: Docker のコンテナをノードにして、手元に Kubernetes のクラスタを作る道具です。
- **ノード**: Pod を動かす場所です。この章の kind では、ノード1台がコンテナ1つです。
- **kubeconfig**: kubectl がクラスタへ接続するための設定ファイルです。既定の場所は `$HOME/.kube/config` です。
