## この章のゴール

- [[NodePort]] の [[Service]] を作り、[[Pod]] への入口を1つにできる
- 自分のパソコンの 127.0.0.1 から、その入口を開くことができる
- [[セレクタ]] が、どの Pod へ届けるかを決めていると説明できる

## 前提

第14章の Deployment `memo` が、名前空間 `memo` で動いています。Pod の [[ラベル]] は `app: memo` です。イメージは `memo:ch13` で、`APP_MESSAGE` はまだ渡していません。返す文字の初期値は `podから` です。

第12章で、kind のコントロールプレーンの 30080 番を、ホストの 127.0.0.1 の 30080 番へつないであります。

Kubernetes の Service は、第9章の [[サービス]] とは別のものです。Compose のサービスは、ファイルの中の1種類のコンテナです。Kubernetes の Service は、ラベルが一致する Pod へ通信を届ける入口です。

実行場所は、Ubuntu の端末です。Windows では、[[WSL2]] の Ubuntu です。この章のコマンドは、どちらも同じです。Windows のブラウザから 127.0.0.1:30080 を開く操作は、この執筆環境では実行していません。

出力が違うとき。 `Permission denied` なら、ホーム以外です。コマンドをコピーし直してください。

2. Service のマニフェストを作ります。

```bash
cat > service.yaml <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: memo
  namespace: memo
spec:
  type: NodePort
  selector:
    app: memo
  ports:
  - port: 8000
    targetPort: 8000
    nodePort: 30080
EOF
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。カレントディレクトリは `$HOME/docker-learn/ch15` です。同じファイルを `samples/ch15/service.yaml` に置いてあります。

`kind: Service` は、これが Service だと API に伝えます。 `metadata.name` と `metadata.namespace` は、どちらも `memo` です。 `spec.type` は、このクラスタの explain では、Service の公開の仕方です。既定は ClusterIP です。 `NodePort` は、ClusterIP に加えて、各ノードの1つのポートでも開きます。 `spec.selector` は、explain では、ラベルの名前と値が一致する Pod へ通信を届ける指定です。ここでは `app: memo` です。これがセレクタです。 `ports.port` は、explain では、この Service が開くポートです。 `8000` にします。 `ports.targetPort` は、explain では、届ける先の Pod のポートです。アプリが待つ `8000` にします。 `ports.nodePort` は、explain では、NodePort のときに各ノードで開くポートです。通常はシステムが割り当てます。値を書き、範囲内で、使われていなければ、その値が使われます。第12章で開けた `30080` を書きます。

期待する出力。

何も表示されません。2026-10-16 にこの執筆環境で実行し、終了ステータスは 0 でした。`samples/ch15/service.yaml` とバイト単位で一致しました。

出力が違うとき。 YAML が画面に出たら、`>` が抜けています。コマンドをコピーし直してください。

```yaml file=samples/ch15/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: memo
  namespace: memo
spec:
  type: NodePort
  selector:
    app: memo
  ports:
  - port: 8000
    targetPort: 8000
    nodePort: 30080
```

3. Service を作ります。

```bash
kubectl apply -f "$HOME/docker-learn/ch15/service.yaml" --context kind-memo
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。 `kubectl apply` は、ファイルの定義をクラスタへ反映します。無ければ作ります。 `-f` は、ファイル名です。 `--context kind-memo` は、接続先です。この執筆環境では、同じ内容の `samples/ch15/service.yaml` を apply しました。出力にファイルのパスは含まれません。

期待する出力。

```text
service/memo created
```

終了ステータスは 0 でした。

出力が違うとき。 `configured` と出たら、すでに同じ名前があります。次の一覧で TYPE が NodePort なら、先へ進んでください。

4. Service の一覧を見ます。

```bash
kubectl get service memo -n memo --context kind-memo
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。 `kubectl get service` は、Service を表示します。 `memo` は、その名前です。 `-n memo` は、名前空間です。 `--context kind-memo` は、接続先です。

期待する出力。

```text
NAME   TYPE       CLUSTER-IP     EXTERNAL-IP   PORT(S)          AGE
memo   NodePort   10.96.230.45   <none>        8000:30080/TCP   0s
```

終了ステータスは 0 でした。AGE は違ってよいです。TYPE が `NodePort` で、PORT(S) が `8000:30080/TCP` であることを、この実行では確認しました。 `8000` が Service のポート、`30080` がノードのポートです。CLUSTER-IP の `10.96.230.45` は、この実行で割り当てられた、クラスタの中から使うアドレスです。この章では、そのアドレスへは接続しません。

出力が違うとき。 TYPE が `ClusterIP` なら、マニフェストの `type: NodePort` が反映されていません。ファイルを見直して、もう一度 apply してください。

5. 自分のパソコンから開きます。

```bash
curl -sS -D - http://127.0.0.1:30080/
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。Windows では、WSL2 の Ubuntu です。 `curl` は、指定した URL へ HTTP で接続します。 `-s` は、help では、進捗を出さない指定です。 `-S` は、help では、`-s` のときでもエラーは出す指定です。 `-D -` は、help の `--dump-header` で、受け取ったヘッダを指定したファイルへ書きます。ファイル名 `-` では、この実行のヘッダが画面に出ました。URL の `127.0.0.1` は、自分のパソコン自身です。 `30080` は、手順4のノードのポートです。

期待する出力。

```text
HTTP/1.0 200 OK
Server: BaseHTTP/0.6 Python/3.12.15
Date: Fri, 16 Oct 2026 18:25:05 GMT
Content-Type: text/plain; charset=utf-8
Content-Length: 9

podから
```

終了ステータスは 0 でした。執筆環境の curl は、ヘッダの改行に CR を含んでいました。上の表示は、その CR を除いたものです。行の文字は同じです。Date は違ってよいです。 `HTTP/1.0 200 OK` と `Content-Length: 9` と、本文の `podから` を確認してください。 `podから` は、`APP_MESSAGE` が無いときのアプリの初期値です。Deployment の Pod まで届いています。

出力が違うとき。 この執筆環境では、最初の同じ curl が次の表示で失敗しました。終了ステータスは 56 でした。

```text
curl: (56) Recv failure: Connection reset by peer
```

原因は、この環境のカーネルが、kube-proxy の iptables モードで使う statistic の照合を持っていなかったことです。確認のため、kube-proxy の ConfigMap の `mode` を `nftables` に変えて、kube-proxy を再起動しました。上の 200 は、そのあとの結果です。通常の Ubuntu では、この切り替えは要りません。手順には入れていません。 `Connection refused` なら、Service の nodePort と、kind の 30080 番の対応を見直してください。本文が `設定から` なら、第16章の設定が先に入っています。この章の時点では `podから` です。

## 壊してみる

開けていないポートへ接続します。

1. 30081 番へ接続します。

```bash
curl -sS -D - --max-time 5 http://127.0.0.1:30081/
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。手順5と同じ curl です。ポートだけ `30081` です。Service は 30080 番を開けています。30081 番は開けていません。 `--max-time` は、curl の help では、転送に許す最大時間です。単位は秒です。 `5` は 5 秒です。待たずに失敗することを、この実行で見ました。

期待する出力。

```text
curl: (7) Failed to connect to 127.0.0.1 port 30081 after 0 ms: Couldn't connect to server
```

終了ステータスは 7 でした。 `200` は出ていません。

出力が違うとき。 `podから` が返ったら、30081 番で何かが待っています。ポート番号を確認してください。

`Couldn't connect to server` は、そのポートで受け取るプログラムが無い、という意味です。番号が1つ違うだけで、Service には届きません。

## 確認テスト

文章で答えてください。新しいコマンドを実行しなくても答えられます。

:::quiz
`type: NodePort` は、ClusterIP と何が違いますか。
:::answer
各ノードの1つのポートでも、同じ Pod へ届くようにします。
:::explain
このクラスタの explain では、NodePort は ClusterIP に加えて、各ノードのポートを割り当てます。この章では 30080 番を指定しました。
:::

:::quiz
`spec.selector` の `app: memo` は、何を選びますか。
:::answer
ラベル `app` の値が `memo` である Pod です。
:::explain
explain では、selector は、ラベルの名前と値が一致する Pod へ通信を届ける指定です。Deployment の Pod にも `app: memo` が付いています。
:::

:::quiz
この章で curl するポートが 8000 ではなく 30080 なのは、なぜですか。
:::answer
8000 は Service と Pod のポートで、自分のパソコンから開いているのはノードの 30080 番だからです。
:::explain
kind は、ホストの 127.0.0.1:30080 を、コントロールプレーンの 30080 番へ渡しています。`ports.port` の 8000 は、その手前の Service のポートです。
:::

## まとめ

- **Service**: ラベルが一致する Pod へ、安定した入口から通信を届けるリソースです。Pod が入れ替わっても、入口の名前は残ります。
- **NodePort**: Service の公開の型の1つです。各ノードの同じポート番号でも、Pod へ届くようにします。
- **セレクタ**: Service が、どの Pod へ届けるかを選ぶラベルの組です。この章では `app: memo` です。

## 片付け

Service は消しません。第16章以降も、127.0.0.1:30080 からアプリを開きます。Deployment と名前空間も残します。
