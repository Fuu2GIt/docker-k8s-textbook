## 確認したバージョン

2026-10-16 に、次を確認しました。

- kind v0.33.0 の `kind delete cluster --help`
- kind v0.33.0 の `kind get clusters --help`
- `kubectl set env --help`
- `kubectl set image --help`
- `kubectl rollout status --help`

クラスタは、この章の削除の前まで Kubernetes v1.37.0 でした。クライアントは kubectl v1.37.1 です。kind の delete は、help では、何度実行しても失敗しない操作です。クラスタが残っていれば消し、すでに無ければ成功で戻ります。 `--name` の既定は `kind` です。この教科書の名前は `memo` なので、必ず `--name memo` を付けます。

`kubectl set env` の help の例では、変数名のうしろに `-` を付けると、その環境変数の定義を外します。例は `ENV-` です。

## この章のゴール

- 文字を変えたアプリをイメージにして、kind のノードへ載せることができる
- [[初期値]] より環境変数が優先されることを、応答の違いで確認できる
- [[クラスタ削除]] で、手元のクラスタを消すことができる

## 前提

第19章までの Deployment、ConfigMap、Secret、Service が、クラスタ `memo` で動いています。応答は `設定から` です。アプリは、環境変数 `APP_MESSAGE` があればその文字を返し、無ければ初期値を返します。

[[総合演習]] は、アプリを自分で作り、イメージにして、Kubernetes で動かすまでの一連の練習です。この章では、初期値を `演習から` に変えます。

実行場所は、Ubuntu の端末です。Windows では、[[WSL2]] の Ubuntu です。この章のコマンドは、どちらも同じです。

    def do_GET(self):

## 何が起きたか

## 壊してみる

存在しないコンテキストを指定します。

1. 無いコンテキストで Pod を見ます。

```bash
kubectl get pods -n memo --context kind-no-such
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。 `--context` は、使う kubeconfig のコンテキストです。 `kind-no-such` は、作っていない名前です。クラスタが残っていても、この名前では接続しません。

期待する出力。

```text
error: context "kind-no-such" does not exist
```

この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 1 でした。Pod の一覧は出ていません。

出力が違うとき。 Pod の表が出たら、コンテキスト名が実在しています。`kind-no-such` をコピーし直してください。

`context was not found` や `does not exist` は、kubeconfig にその接続先が無い、という意味です。クラスタの Pod が悪い、というエラーではありません。

## 確認テスト

文章で答えてください。新しいコマンドを実行しなくても答えられます。

:::quiz
イメージを `memo:ch21` に変えた直後、応答が `設定から` のままだったのは、なぜですか。
:::answer
環境変数 `APP_MESSAGE` が残っていて、初期値より優先されたからです。
:::explain
アプリは `APP_MESSAGE` があればその文字を返します。初期値の `演習から` は、環境変数が無いときだけ使います。
:::

:::quiz
`APP_MESSAGE-` の末尾の `-` は、何をしますか。
:::answer
その環境変数の定義を外します。
:::explain
`kubectl set env --help` の例では、`ENV-` が環境変数 ENV を外す書き方です。
:::

:::quiz
`kind delete cluster` で `--name` を省略すると、どの名前を消しますか。
:::answer
既定の `kind` です。この教科書のクラスタ名 `memo` は消えません。
:::explain
help では、`--name` の既定は `kind` です。この章では `--name memo` を付けます。
:::

## まとめ

- **総合演習**: アプリを自分で作り、イメージにして、Kubernetes で動かすまでの一連の練習です。
- **初期値**: 環境変数が無いときに、アプリが使う文字です。環境変数があると、初期値は使われません。
- **クラスタ削除**: kind のクラスタと、そのノードのコンテナを消す操作です。`kind delete cluster --name memo` がそれを行います。

出力が違うとき。 `No kind clusters found` と出るコマンドは、次の一覧です。delete が成功の行を出さなくても、終了ステータスが 0 なら、次で確認してください。

2. クラスタの一覧を見ます。

```bash
kind get clusters
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。 `kind get clusters` は、残っている kind のクラスタ名を出します。

期待する出力。

```text
No kind clusters found.
```

この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 0 でした。 `memo` は出ていません。

出力が違うとき。 `memo` が残っているなら、手順1の `--name memo` が付いていません。もう一度、名前を付けて消してください。

3. 消したあとのコンテキストを指定します。

```bash
kubectl get nodes --context kind-memo
```

何をするコマンドか。 実行場所は、Ubuntu の端末です。クラスタを消したあと、以前のコンテキスト `kind-memo` でノードを見ます。kind は、削除のときにそのコンテキストも外します。

この出力は、2026-10-16 にこの執筆環境で実行した結果です。終了ステータスは 1 でした。ノードの表は出ていません。接続先の名前が、kubeconfig から無くなっています。

出力が違うとき。 ノードの表が出たら、クラスタがまだ残っています。手順2で `memo` が無いかを確認してください。
